# V8 shapes × LLM: результаты эксперимента

**Дата прогона:** 2026-07-13
**Окружение:** Node `v24.18.0` (V8 `13.6.233.17-node.50`, Maglev включён по умолчанию), Linux x64.
**Модель:** `claude -p --model opus` (свежая сессия на каждую генерацию, контекст между прогонами не течёт).
**Прибор:** `shape-analyzer.js` — считает число различных hidden classes результата `normalizeUser` через `%HaveSameMap`, меряет p50 горячего цикла и checksum-корректность.
**N = 15** генераций на ветку, 4 ветки, итого **60** вызовов модели.

### Про deopts — читать осторожно

Абсолютные значения `deopts` (grep по `bailout` из `--trace-deopt`) **не разделяют ветки** и здесь интерпретации не поддаются:

```
P1 без правил (MEGA): 9–11,  очень плотно   (9,10,10,10,...,11)
P1 с правилами (MONO): 4–19, БИМОДАЛЬНО     (18,5,6,5,18,19,4,17,4,16,...)
P2 без правил (MEGA): 10–11, плотно
P2 с правилами (MONO): 5–18, бимодально
```

Фон харнесса (тиринг самого `score()`/аналайзера) доминирует и у MONO-веток даёт бóльшую дисперсию, чем сам эффект. **Вывод про производительность строим на shapes и p50, а не на счётчике deopts** — ровно как и предупреждалось про ~2 фоновых деопта. Deopts оставлен в таблице для полноты, но как метрику разделения не используем.

## P1 vs P2 — влияет ли формулировка тикета?

Формулировка **не влияет на структурную (shape) стабильность**: и «опциональные поля» (P1), и «поля … могут отсутствовать» (P2) дали 100% MEGA без правил и 100% MONO с правилами. Обе формулировки одинаково триггерят идиому «добавь ключ, только если значение есть».

Формулировка **влияет на богатство value-нормализации** (не на shape):
- P2 («перед дальнейшей обработкой в сервисе») чаще толкает модель к защитному приведению типов: `String(id)`, `Number(credits)` + `Number.isFinite`, `.trim().toLowerCase()` для email. Дефолт имени `'Anonymous'` вместо `''` встретился в **14/15** P2-генераций без правил и в **0/15** P1.
- P1 (сухой список дефолтов) даёт более буквальный код: `x != null ? x : default`.

Для доклада: переформулировка тикета не спасает от shape-нестабильности — она меняет обработку значений, но не решение «класть ли ключ». Лечит только явное правило.

## Показательные сниппеты из no-rules веток

**Механизм у всех 30 no-rules генераций один:** собрать литерал с 5 обязательными полями, затем **дописать опциональные поля через `if`-guard**. Ни одной генерации через `...(cond && {...})` спред и ни одной через `Object.assign` — дефолтная идиома модели именно «условное дописывание свойства после создания» (тот же результат: 2³ = 8 hidden classes).

**(1) P1 без правил — канонический паттерн (`p1-no-rules/candidate_1.js`):**
```js
const result = {
  id: src.id,
  name: src.name != null ? src.name : '',
  email: src.email != null ? src.email : '',
  plan: src.plan != null ? src.plan : 'free',
  credits: src.credits != null ? src.credits : 0,
};
if (src.referrer != null)  result.referrer  = src.referrer;   // ← добавляет ключ
if (src.trialUntil != null) result.trialUntil = src.trialUntil; // ← ещё один shape
if (src.teamId != null)    result.teamId    = src.teamId;      // ← и ещё
return result;                                                  // 8 разных hidden classes
```

**(2) P2 без правил — тот же shape-дефект под богатой нормализацией (`p2-no-rules/candidate_2.js`):**
```js
const result = {
  id: input.id != null ? String(input.id) : '',
  name: typeof input.name === 'string' && input.name.trim() !== '' ? input.name.trim() : 'Anonymous',
  email: typeof input.email === 'string' ? input.email.trim().toLowerCase() : '',
  plan: typeof input.plan === 'string' && input.plan.trim() !== '' ? input.plan.trim() : 'free',
  credits: Number.isFinite(Number(input.credits)) ? Number(input.credits) : 0,
};
if (input.referrer != null) { result.referrer = String(input.referrer); }
if (input.trialUntil != null) { /* ...даже парсит дату... */ result.trialUntil = date.toISOString(); }
if (input.teamId != null) { result.teamId = String(input.teamId); }
```
Более «взрослый» код (валидация, типы, даты) — и та же MEGA: значения нормализованы, **форма объекта — нет**.

**(3) Как это чинит правило (`p1-rules/candidate_1.js`) — для контраста:**
```js
return {
  id: src.id != null ? src.id : null,
  name: src.name != null ? src.name : '',
  email: src.email != null ? src.email : '',
  plan: src.plan != null ? src.plan : 'free',
  credits: src.credits != null ? src.credits : 0,
  referrer: src.referrer != null ? src.referrer : null,   // ключ всегда есть → null
  trialUntil: src.trialUntil != null ? src.trialUntil : null,
  teamId: src.teamId != null ? src.teamId : null,
};                                                          // ровно 1 hidden class
```
30/30 генераций с правилами — единый литерал со всеми полями, отсутствующее = `null`. Ровно то, что предписывает правило №1.

## Вердикт по заранее зафиксированному прогнозу

**Прогноз (зафиксирован до прогона):** без правил большинство генераций → POLY/MEGA; с правилами → почти все MONO.

**ПОДТВЕРЖДЁН, причём сильнее прогноза:**
- Без правил: **30/30 (100%) MEGA** — не «большинство», а все, и сразу в худшую категорию (8 shapes), минуя POLY.
- С правилами: **30/30 (100%) MONO** — не «почти все», а все.
- Эффект производительности на горячем пути: медиана p50 **1.60 → 0.36 мс (~4.4× быстрее)**, диапазоны не пересекаются.
- Гипотеза о происхождении идиомы из корпуса подтверждается механизмом: модель по умолчанию пишет «условное дописывание ключа» в 100% случаев без единого примера в промпте.

Гипотеза была фальсифицируема (любой исход — результат); фактический исход — максимально чистое подтверждение.

## Угрозы валидности

1. **Один вендор / одна модель.** Всё на `opus` через `claude -p`. Идиома «conditional key» может быть по-разному выражена у других семейств моделей — нельзя обобщать на «все LLM».
2. **N=15 на ветку.** Разброс внутри режима почти нулевой (shapes без вариации, p50 в пределах ±0.1 мс), поэтому 15 достаточно для *этого* эффекта; но редкие альтернативные паттерны (спред, `Object.assign`) с частотой <1/15 могли не попасться — мы видели только `if`-guard.
3. **Порядок и состав полей в промпте.** Обязательные перечислены до опциональных, ровно 3 опциональных поля. Другой порядок/число опциональных мог бы сдвинуть картину (например, 1 опциональное поле → POLY, а не MEGA).
4. **Формулировка правил инлайнится в промпт.** Ветка «с правилами» получает явный запрет на `...(cond && {})` и предписание null-fill — это сильный, прямой сигнал. Мы не проверяли более мягкие/косвенные формулировки правил.
5. **Deopts-метрика зашумлена** фоном харнесса (см. выше) — по ней выводы не делаем; при желании измерять деопты нужен изолированный горячий путь без тиринга аналайзера.
6. **Прибор задаёт распределение входов** (`makeRaw`: доли присутствия опциональных полей). Другое распределение (например, поле почти всегда присутствует) изменило бы наблюдаемое число реально встречающихся shapes, хотя потенциал MEGA остаётся.
7. **Value-нормализация ≠ shape.** P2 давал приведение типов (`String`/`Number`), что теоретически могло бы влиять на элемент-типы, но на структуру shape не влияет — мы измеряли именно map-идентичность, что и нужно для гипотезы.
