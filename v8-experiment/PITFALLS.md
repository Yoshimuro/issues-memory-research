# Грабли: как мерить V8 и не обмануть себя

Всё ниже — не теория, а то, на что я наступил сам, пока готовил доклад «V8 для самых маленьких» (HolyJS, 24.10.2026). Каждый пункт воспроизводится командами из этого репозитория.

## Замер

**Гонять кейсы подряд в одном процессе — значит мерить заражение, а не кейс.**
Записи мест чтения (inline caches) и обратная связь по типам не сбрасываются между кейсами. Классический пример — «try/catch дорогой»: в одном процессе пара даёт 22 против 66 мс (×3), в отдельных процессах — 14 против 14. Кратность была артефактом бенча: общий цикл замера оптимизировался под первую функцию, а вторая сломала эту ставку (`--trace-deopt`: `wrong call target` в `naiveBench`).
`docker/run.sh 24 'cd demos/myths && …'` — каждый кейс отдельным процессом.

**Первые прогоны после старта могут быть мусором.**
В прогоне 19.09 первая серия генераций показала p50 3.5–3.9 мс при эталоне 0.8 — помеха на машине. Лечится контрольным замером эталона до и после серии (`candidates-control.jsonl`); если контроль разошёлся — серия бракуется. Забракованные данные сохранены рядом (`*-disturbed.jsonl`), а не удалены.

**Медиана, а не среднее; пять повторов, а не один.**
На arm64 тот же бенч между прогонами гуляет на единицы процентов, на общих CI-раннерах — на четверть.

**Считайте контрольную сумму результата.**
Иначе легко сравнить быстрый код с кодом, который делает меньше работы. В пайплайне `semanticSink` совпал во всех 150 прогонах (5 вариантов × 2 батча × 3 R × 5 повторов) — это и есть доказательство, что варианты эквивалентны.

## Флаги и трейсы

**`--trace-ic` удалён из V8 9.3** (2021; до этого был лишь алиасом `--log-ic`). Живой флаг — `--log-ic`. Старые статьи с `--trace-ic` дадут «bad option».

**`--log-ic` без `--no-logfile-per-isolate` пишет файл с адресом изолята в имени** (`isolate-0x…-v8.log`) — на сцене не запускать, собирать заранее:
```
node --allow-natives-syntax --log-ic --no-logfile-per-isolate --logfile=ic.log lab/shape-analyzer.js lab/ref-b.js > /dev/null
grep '^LoadIC' ic.log | grep ',30,9,' | cut -d, -f1,4-9
```
Сырая строка журнала: тип, pc, время, строка, колонка, было, стало, адрес формы, имя поля; `cut -d, -f1,4-9` оставляет тип, строку, колонку, было, стало, форму, поле. Фильтр `,30,9,` — место `u.plan` в читателе `score`. Без него `grep ,plan` захватит и чтение `raw.plan` в `normalizeUser` (строка 8 `ref-*.js`), где у A тоже есть P и N: сырые входы разной формы. У B по `u.plan`: `0→1`, `1→P`, `P→P`, `P→P`, `P→N`, `N→N`; у A — одна строка `0→1`.

**`--trace-deopt` без фильтра по функции обманывает.**
Строка `reason: wrong map` есть и у «хорошей» версии — но в другой функции: в самой `normalizeUser` (у неё меняется форма *входной* записи) и в анонимной обёртке модуля. Смотреть нужно только на читателя:
```
node --allow-natives-syntax --trace-deopt lab/demo-wrongmap.js lab/ref-b.js | grep 'JSFunction score'
```
У читателя B — 5 прогонов из 5, у читателя A — 0 из 5.

**В приборе `wrong map` нет вообще, и это не ошибка.**
Если читатель с первого вызова видит все восемь форм, ставки на одну форму не было — ломаться нечему. Он один раз компилируется TurboFan и всё равно работает в шесть с лишним раз медленнее. Деопт — событие, цена — стационарный общий путь. Чтобы увидеть событие, нужен сценарий «привык к одной форме → пришла другая» (`lab/demo-wrongmap.js`).

**Общий счётчик деоптов по процессу как метрика не годится** — его засоряет сам харнесс: у одноформной ветки разброс 4–19, у восьмиформной 9–11. Считать только по имени интересующей функции.

**`--no-turbofan` не выключает спекуляцию** — остаётся Maglev, а `%OptimizeFunctionOnNextCall` под ним ничего не делает. Чтобы зажать ярус, есть `--max-opt=0|1|2|3`.

**Какой ярус у функции — смотреть по имени функции, а не на глаз.** Без интринсиков: `--log-function-events --logfile=fe.log --no-logfile-per-isolate` (история interpreter → baseline → maglev → turbofan по имени), `--trace-opt` / `--trace-deopt` (события; «took a, b, c ms» — три фазы, складывать), `--prof` + `--prof-process` (префиксы `~ ^ + *`). С `--allow-natives-syntax` — `%GetOptimizationStatus`: биты зависят от версии V8. `docker/shape-analyzer-status.js` проверяет, что читатель у A и B в стационаре на TurboFan (статус 81), — значит, B медленный не потому, что не скомпилировался. Профайлер DevTools и `--cpu-prof` ярус не показывают.

## Версии и архитектуры

**Node 20 и Node 22 (с 22.9.0) собраны без Maglev** (`node -p process.config.variables.v8_enable_maglev` → 0; в Node 22.9.0 откатили включение Maglev из 22.0.0, nodejs/node#54384). Флаг `--maglev` принимается, но ничего не включает: `%OptimizeMaglevOnNextCall` печатает «Maglev is not enabled.», в `--trace-opt` ноль строк MAGLEV. Поэтому на Node 22 `--max-opt=2` равен `--max-opt=1` (762 ≈ 763 мс), а TurboFan приходит на ~4 700-м вызове вместо ~13 000. Для сравнения ярусов годится только Node 24.

**«Sparkplug на ~700-м вызове» — не порог.** Sparkplug компилирует пачками (`--baseline-batch-compilation`); одна маленькая функция в бенче пачку не набирает и ждёт. С `--no-baseline-batch-compilation` он приходит на 9-м вызове (Node 22 и 24). В приложении с тысячами функций пачка набирается быстро.

**`--always-turbofan` не значит «всё сразу в TurboFan».** На Node 22/24 функцию берут в оптимизацию не раньше второго вызова (`--minimum-invocations-before-optimization=2`): в `npm --version` запросов на оптимизацию сотни, а TurboFan-код получают считаные функции — и старт всё равно вдвое дольше. На Node 20 флаг и правда компилирует всё, и горячий код выходит медленнее обычного: ставить было не на что. В V8 14+ флага нет (`bad option`).

**«TurboFan приходит на N-м вызове» — верно только для функций без циклов.** Считаются вызовы и витки циклов внутри функции; размер ни при чём — бюджет пропорционален длине байткода, и длина сокращается. Замер (`docker/tier-when.js`, Node 24.21): функция в 5 строк и функция в 50 строк без циклов дают одно и то же — Maglev ~1000–1500, TurboFan ~13–16 тыс. вызовов (без фоновой компиляции, `--no-concurrent-recompilation`: 511 и ~10 600 — это замер, не номиналы 400 / 3000 из flag-definitions: пока фоновый компилятор работает, функция продолжает исполняться на прежнем ярусе). Функция с циклом по 200 объектам внутри — Maglev ~60, TurboFan ~1500 (без фоновой очереди — 4 и 77). По времени у всех одно и то же: первые 2–5 мс горячей работы.

**Эмуляция чужой архитектуры (`docker --platform linux/amd64` на Apple Silicon) не годится для чисел** — транслятор искажает JIT. Для проверок «да/нет» — можно; для миллисекунд — нет. Настоящий x64 гоняется в GitHub Actions (`.github/workflows/v8-talk-verify.yml`).

**Множители зависят от машины, направление — нет.** Прибор: ×6.6 на arm64, ×4.4 на x64. HTTP: ×1.95 против ×1.69. Смешивать числа из разных окружений в одном отчёте нельзя; окружение подписывается один раз (`docker/out/*/env.txt`).

**Один бенч может быть бимодальным.** На Node 20 чтение восьми форм против одной даёт то ×3.6, то ×14 в соседних прогонах. Такое число нельзя называть — только показывать разброс.

## Запуск

**Прибор запускать из `v8-experiment/`.** В корневом `package.json` стоит `"type": "module"`; `v8-experiment/package.json` с `"type": "commonjs"` возвращает `lab/*.js` в CommonJS. Без него прибор падает с `require is not defined`.

**`%`-интринсики требуют `--allow-natives-syntax`** и в проде недоступны. `%HaveSameMap` — счётчик форм, `%GetOptimizationStatus` — статус яруса, `%NeverOptimizeFunction` — чтобы горячий цикл не поглотил измеряемую функцию (иначе она не поднимается по ярусам сама).

**В d8 `%OptimizeFunctionOnNextCall` без предшествующего `%PrepareFunctionForOptimization` падает** (`Fatal error … CheckMarkedForManualOptimization`; проверено на d8 15.6). Без интринсиков d8 поднимает функции по ярусам сам, как Node.

## Как перепроверить всё разом

```
git clone -b v8-talk-verify https://github.com/Yoshimuro/issues-memory-research
cd issues-memory-research/v8-experiment
./docker/run.sh 24 'bash docker/verify.sh my-run && node docker/report.js docker/out/my-run'
```
~25 минут, строго последовательно. Результат — `docker/out/my-run/NUMBERS.md`. На время прогона машину не нагружать.
