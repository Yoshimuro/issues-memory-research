# Грабли: как мерить V8 и не обмануть себя

Всё ниже — не теория, а то, на что я наступил сам, пока готовил доклад «V8 для самых маленьких» (HolyJS, 24.10.2026). Каждый пункт воспроизводится командами из этого репозитория.

## Замер

**Гонять кейсы подряд в одном процессе — значит мерить заражение, а не кейс.**
Записи мест чтения (inline caches) и обратная связь по типам не сбрасываются между кейсами. Классический пример — «try/catch дорогой»: в одном процессе пара даёт 21 против 65 мс (×3), в отдельных процессах — 13 против 13. Кратность была артефактом бенча.
`docker/run.sh 24 'cd demos/myths && …'` — каждый кейс отдельным процессом.

**Первые прогоны после старта могут быть мусором.**
В прогоне 19.09 первая серия генераций показала p50 3.5–3.9 мс при эталоне 0.8 — помеха на машине. Лечится контрольным замером эталона до и после серии (`candidates-control.jsonl`); если контроль разошёлся — серия бракуется. Забракованные данные сохранены рядом (`*-disturbed.jsonl`), а не удалены.

**Медиана, а не среднее; пять повторов, а не один.**
На arm64 тот же бенч между прогонами гуляет на единицы процентов, на общих CI-раннерах — на четверть.

**Считайте контрольную сумму результата.**
Иначе легко сравнить быстрый код с кодом, который делает меньше работы. В пайплайне `semanticSink` совпал во всех 150 ячейках — это и есть доказательство, что варианты эквивалентны.

## Флаги и трейсы

**`--trace-ic` удалён из V8 9.4.** Живой флаг — `--log-ic`. Старые статьи с `--trace-ic` дадут «bad option».

**`--log-ic` без `--no-logfile-per-isolate` пишет файл с адресом изолята в имени** (`isolate-0x…-v8.log`) — на сцене не запускать, собирать заранее:
```
node --allow-natives-syntax --log-ic --no-logfile-per-isolate --logfile=ic.log lab/shape-analyzer.js lab/ref-b.js
grep '^LoadIC' ic.log | grep ,plan
```
Колонки: тип, строка, колонка, состояние «было», состояние «стало», адрес формы, имя поля. У B по полю `plan`: `0→1`, `1→P`, `P→P`, `P→N`, `N→N`; у A — одна строка `0→1`.

**`--trace-deopt` без фильтра по функции обманывает.**
Строка `reason: wrong map` есть и у «хорошей» версии — но в другой функции: в самой `normalizeUser` (у неё меняется форма *входной* записи) и в анонимной обёртке модуля. Смотреть нужно только на читателя:
```
node --allow-natives-syntax --trace-deopt lab/demo-wrongmap.js lab/ref-b.js | grep 'JSFunction score'
```
У читателя B — 5 прогонов из 5, у читателя A — 0 из 5.

**В приборе `wrong map` нет вообще, и это не ошибка.**
Если читатель с первого вызова видит все восемь форм, ставки на одну форму не было — ломаться нечему. Он один раз компилируется TurboFan и всё равно работает в шесть с лишним раз медленнее. Деопт — событие, цена — стационарный общий путь. Чтобы увидеть событие, нужен сценарий «привык к одной форме → пришла другая» (`lab/demo-wrongmap.js`).

**Общий счётчик деоптов по процессу как метрика не годится** — его засоряет сам харнесс: у одноформной ветки разброс 4–19, у восьмиформной 9–11. Считать только по имени интересующей функции.

**`--no-turbofan` не выключает спекуляцию** — остаётся Maglev, а `%OptimizeFunctionOnNextCall` под ним ничего не делает. Чтобы зажать ярус, есть `--max-opt=0|1|2|3`.

**`%GetOptimizationStatus` — единственный честный способ проверить, что код действительно оптимизирован** (а не «медленный, потому что не скомпилировался»): `docker/shape-analyzer-status.js`.

## Версии и архитектуры

**Node 22 идёт без Maglev по умолчанию** (`--no-maglev` в 22.16+). Поэтому `--max-opt=2` там равен `--max-opt=1` (762 ≈ 763 мс), а TurboFan приходит на ~4 700-м вызове вместо ~13 000. Для сравнения ярусов нужен Node 24 или явный `--maglev`.

**«TurboFan приходит на N-м вызове» — такого числа нет.** Движок считает не вызовы, а исполненный байткод, а компилирует в фоновом потоке. Замер (`docker/tier-when.js`, Node 24.21): крошечная функция без циклов — Maglev ~1000–1500, TurboFan ~13–15 тыс. вызовов; функция с циклом по 200 объектам внутри — Maglev ~60, TurboFan ~1500. По времени у всех одно и то же: первые 2–5 мс горячей работы. Без фоновой очереди (`--no-concurrent-recompilation`) видны номиналы: Maglev на 511-м вызове, TurboFan на ~10 600-м для функций без циклов и на 77-м для функции с циклом. Мерить пороги на одной крошечной функции и обобщать — ошибка, которую я сделал сам.

**Эмуляция чужой архитектуры (`docker --platform linux/amd64` на Apple Silicon) не годится для чисел** — транслятор искажает JIT. Для проверок «да/нет» — можно; для миллисекунд — нет. Настоящий x64 гоняется в GitHub Actions (`.github/workflows/v8-talk-verify.yml`).

**Множители зависят от машины, направление — нет.** Прибор: ×6.6 на arm64, ×4.4 на x64. HTTP: ×1.95 против ×1.69. Смешивать числа из разных окружений в одном отчёте нельзя; окружение подписывается один раз (`docker/out/*/env.txt`).

**Один бенч может быть бимодальным.** На Node 20 чтение восьми форм против одной даёт то ×3.6, то ×14 в соседних прогонах. Такое число нельзя называть — только показывать разброс.

## Запуск

**Из корня репозитория прибор не стартует.** В корневом `package.json` стоит `"type": "module"`, поэтому `lab/*.js` грузятся как ESM и падают с `require is not defined`. Варианты: контейнер (`docker/run.sh`), копия папки `lab` вне репозитория или `v8-experiment/package.json` с `"type": "commonjs"`.

**`%`-интринсики требуют `--allow-natives-syntax`** и в проде недоступны. `%HaveSameMap` — счётчик форм, `%GetOptimizationStatus` — статус яруса, `%NeverOptimizeFunction` — чтобы горячий цикл не поглотил измеряемую функцию (иначе она не поднимается по ярусам сама).

**d8 15.2 сам ничего не оптимизирует без `%PrepareFunctionForOptimization`** — забудете вызов, получите сравнение двух интерпретаторов.

## Как перепроверить всё разом

```
git clone -b v8-talk-verify https://github.com/Yoshimuro/issues-memory-research
cd issues-memory-research/v8-experiment
./docker/run.sh 24 'bash docker/verify.sh my-run && node docker/report.js docker/out/my-run'
```
~25 минут, строго последовательно. Результат — `docker/out/my-run/NUMBERS.md`. На время прогона машину не нагружать.
